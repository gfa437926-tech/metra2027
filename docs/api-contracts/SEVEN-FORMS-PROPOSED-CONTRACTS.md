# عقود مقترحة للتنفيذ — النماذج السبعة (قابلة للاعتماد)

**الحالة:** تصميم للمراجعة والاعتماد — **غير منفَّذ** على Backend/DB.  
**الفرع المرجعي:** `feat/phenomenon-observation-submit-2026-11-16`  
**مصادر الحقول:** كتالوج Flutter `ObservationFieldCatalogs` + PR #53.  
**العقود الخادمية المعتمدة اليوم فقط:** `hourly` | `daily` | `phenomenon`.

---

## 0. مبادئ مشتركة (كل نموذج رصدي من المجموعة 1–4)

### 0.1 الهوية والمحطة (خادم فقط)

| عنصر | المصدر | ملاحظة |
|---|---|---|
| `userId` | JWT `sub` | لا يُقبل من الجسم |
| `stationId` | مسار URL | يُعاد التحقق من التكليف والصلاحية |
| الدور | لا يُستنتج من الاسم | فقط رموز صلاحيات RPC |

### 0.2 قالب إرسال مقترح (بعد الموافقة — لا يوسَّع الكود قبلها)

```
POST /api/v1/stations/{stationId}/observations
Authorization: Bearer <access_token>
Permission: انظر مصفوفة الصلاحيات لكل نوع

{
  "idempotencyKey": "string ≤128، trim، مطلوب",
  "observationType": "<code>",
  "observedAt": "ISO-8601 UTC",
  "payload": { /* حقول الكتالوج */ },
  "submit": true | false
}
```

| رمز | المعنى |
|---|---|
| 200/201 | قبول |
| 400 | Guard (مفتاح/نوع/حمولة) |
| 401 | غير مصادق |
| 403 | بلا صلاحية / خارج المحطة |
| 409 | تعارض idempotency |
| 422 | فشل التحقق المجالي |
| 503 | خدمة الحفظ غير مهيأة |

**التحقق المقترح:** `POST /api/v1/observations/{code}/validate` — هيكلي فقط بعد JWT (نفس سياسة Fallback الحالية).

### 0.3 المسودة والإرسال والمراجعة (رصد)

| مرحلة | سلوك مقترح |
|---|---|
| مسودة محلية | موجودة الآن في Flutter (`ObservationDraftStore`) — تبقى حتى عقد خادمي |
| مسودة خادمية `submit:false` | اختيارية بعد الموافقة؛ تتطلب `create` و/أو `edit_own_draft` |
| إرسال نهائي `submit:true` | `create` + (بعد قرار منفصل) ربما `submit` |
| مراجعة | طابور `status=submitted` لنفس `stationId` |
| اعتماد / إرجاع | نفس نمط hourly/daily إن بقي ضمن observation |

### 0.4 منع التكرار والتدقيق

- **Idempotency:** مفتاح العميل + فرض RPC (نفس نمط `metra_submit_observation`).
- **Audit:** من أنشأ، متى، المحطة، النوع، القرار، الملاحظات — عبر سجل موجود أو توسعة معتمدة لاحقاً.
- **أخطاء عربية** عبر طبقة العرض الحالية؛ لا تسريب أسرار.

### A1) `rainfall` — رصد الأمطار

| بند | التعريف |
|---|---|
| الغرض | تسجيل هطول/ثلج مرتبط بمحطة وتاريخ رصد |
| **ليس** | ليس بديلاً عن daily.precipitation وحده؛ تقرير مخصّص للأمطار |

**الحقول (ترتيب الكتالوج)**

| # | id | label | النوع المقترح | مطلوب | حدود/وحدات |
|---|---|---|---|---|---|
| 1 | currentDate | تاريخ إرسال | date أو text→date | لا | yyyy-MM-dd |
| 2 | localTime | وقت محلي | time | لا | HH:mm[:ss] |
| 3 | utcTime | UTC | text/time | لا | ساعة مرجعية |
| 4 | rainAmount | هطول مم | decimal | لا | ≥0، وحدة mm |
| 5 | snowDepth | ثلج سم | decimal | لا | ≥0، وحدة cm |
| 6 | observationDate | تاريخ رصد | date | **نعم** | yyyy-MM-dd |
| 7 | responsibilityAgreement | إقرار | boolean | **نعم** | true عند الإرسال |

**مصدر البيانات:** إدخال راصد.  
**صلاحيات مقترحة:** `observation.create` / `edit_own_draft` / `submit`؛ مراجعة اختيارية بنفس رموز review إن دُمج في طابور الأرصاد.  
**Flutter:** `CatalogObservationScreen` + لافتة محلي — جاهز محلياً بعد ملء الاختيارات حيث لزم.  
**ينقص خادماً:** قبول `observationType=rainfall` في guard + validator + RPC/جدول.

## المجموعة ب — بلاغات أعطال / صيانة (workflow مستقل)

> **لا تُفرض** دورة `draft → submitted → approved` الخاصة بالرصد الجوي تلقائياً.

### دورة عمل مقترحة للأعطال (equipment / telecom / IT)

```
reported → assigned → in_progress → resolved → closed
              ↘ returned_for_info (طلب استكمال من المبلّغ)
```

| حالة | المعنى |
|---|---|
| reported | بلاغ مُنشأ |
| assigned | مُسند لمعالج |
| in_progress | قيد المعالجة |
| resolved | أُغلق فنياً بانتظار تأكيد |
| closed | مغلق نهائياً |
| returned_for_info | يحتاج بيانات من المبلّغ |

**صلاحيات مقترحة (رموز جديدة — لا تُمنح لأي دور قبل الموافقة):**

| رمز | عملية |
|---|---|
| `fault.report` | إنشاء بلاغ |
| `fault.edit_own` | تعديل بلاغ المبلّغ قبل الإسناد |
| `fault.assign` | إسناد |
| `fault.resolve` | تسجيل الحل |
| `fault.close` | إغلاق نهائي |
| `fault.review` | مراجعة جودة البلاغ |

بديل مؤقت (أضعف): إعادة استخدام `observation.*` — **غير موصى به** لخلط الرصد بالصيانة.

### B1) `faultequipment` — أعطال الأجهزة

حقول: نوع العطل، وصف، شدة، صورة (غير مفعّلة محلياً)، عاجل، قسم قياس يدوي (نوع/مشكلة/وصف/وقت/شدة/صورة/عاجل)، مفاتيح تضمين تفاصيل/اتصال/حالة.

### B2) `faulttelecom` — أعطال الاتصالات

حقول أجهزة اتصالات (هاتف، برج، قمر، فاكس، حاسوب، لابتوب، طابعة، شبكة، واي فاي) + وصف + عاجل. أغلبها مطلوب في الكتالوج الحالي — قد يُخفَّف لاحقاً بموافقة (نموذج «أقسام اختيارية»).

### B3) `faultit` — بلاغات تقنية المعلومات

مبلّغ (اسم/منصب/هاتف)، نوع نشرة، مجال/نوع مشكلة، وصف، أهمية، فلاتر اختيارية للعرض.

## متطلبات Flutter المشتركة (محلي الآن / بعد العقد)

1. الإبقاء على لافتة «تحقق محلي فقط» حتى يُعتمد الحفظ.  
2. مسودة محلية حسب `stationId` + `formCode`.  
3. RTL ورسائل عربية.  
4. عدم استدعاء `submitObservation` لأنواع غير hourly/daily/phenomenon (مفروض في العميل حالياً).  
5. بعد الموافقة: شاشات متصلة بنفس نمط hourly مع أنواع جديدة.
