# Manual report archive register and monthly completeness report

Date: 2026-11-10  
Target: `gfa437926-tech/metra2027`

## Purpose and boundary

This feature records a human-confirmed archival action for exported Excel report files. It does **not** move observation rows into the primary METRA database and does **not** upload or copy those rows into any application database.

The operator exports the approved reports to Excel, then manually archives those files in a separate archive database/process. The METRA application records that the auditor completed that external archival step so it is not forgotten or repeated accidentally.

The application must not connect to, write to, or synchronize with the archive database as part of this workflow. The archive database is separate from the primary operational database. No legacy database is involved.

## UTC-only rule

- All timestamps are stored and displayed as UTC.
- API timestamps must carry an explicit UTC designator (`Z` or `+00:00`).
- Monthly periods are defined by UTC calendar boundaries: first day 00:00:00 UTC through (but excluding) the first day of the next month 00:00:00 UTC.
- Do not render, calculate, or label a local-time equivalent anywhere in this workflow.
- Observation period start/end values describe the observations contained in the Excel export; archive-completed time describes when the auditor confirmed the external archival action.

## Auditor workflow

1. Open the **سجل أرشفة التقارير** page.
2. Select a reporting month (UTC month) and filter by station, report family, or archive status.
3. Review the list of export batches/files eligible for archival.
4. Export/download the approved Excel file using the existing report export function.
5. Complete the external manual archive operation in the separate archive system/database.
6. Return to METRA and record the completed action:
   - exact exported file name;
   - SHA-256 digest of the file, calculated from the exported bytes;
   - file size in bytes;
   - row/record count represented by the export;
   - station and report family;
   - observation period start/end in UTC;
   - external archive reference or batch identifier (not credentials or connection details);
   - auditor identity from the authenticated session, never from a client-supplied actor ID;
   - archive completion timestamp generated by the server in UTC;
   - optional explanatory note.
7. Confirm the action. The UI must display success only after the server confirms that the audit record was saved.
8. A completed archive action is immutable. Corrections are recorded as a new superseding event with a reason; do not silently edit or delete the original audit event.

## Status model

- **بانتظار الأرشفة** — an export exists but no auditor completion event has been recorded.
- **مؤرشفة يدوياً** — the auditor has confirmed the external archive and the server has recorded the event.
- **تحتاج مراجعة** — file metadata, digest, row count, reporting period, or external reference needs reconciliation.
- **ملغاة** — the export batch was invalidated; retain its audit history and cancellation reason.

A report is not marked archived merely because it was downloaded or exported. Only the auditor's explicit completion action changes the status.

## Monthly report

The **التقرير الشهري للأرشفة والنواقص** is generated for a selected UTC month and contains two distinct sections.

### A. Archive completion

- number of eligible export batches;
- number and percentage manually archived;
- number still awaiting archival;
- number requiring reconciliation;
- number cancelled, with reasons;
- breakdown by station and report family;
- each file name, SHA-256, size, record count, observation UTC period, auditor and archive-completed UTC timestamp;
- duplicate file digests or overlapping export batches flagged for review, not silently merged.

### B. Missing records and missing data

The Head of Network Department defines/records missing items. The auditor's monthly report must show those items and their current state without inventing or automatically resolving them.

Each missing-item record includes:
- station and report family;
- affected observation/report UTC period;
- missing record vs missing field/data classification;
- exact missing field codes or expected report references;
- reason/context supplied by the Head of Network Department;
- identified-by identity and identified-at UTC timestamp;
- responsible unit/person, if assigned;
- status: open, under follow-up, supplied, verified, or closed;
- evidence/reference and closure note, where applicable;
- status-change audit history.

The report must distinguish **missing records** from **incomplete data inside an existing record**. A completed archive action does not imply that the underlying observations are complete.

## Access and audit rules

- Auditor: may view the permitted report scope, register a manual archive completion, and generate monthly archive/completeness reports.
- Head of Network Department: may define and update missing-record/missing-data findings within the approved authority scope.
- Station manager: may view only the station-scoped records permitted by the approved role policy; cannot mark an archive action as completed unless separately authorized as an auditor.
- All actor identities are derived from the verified authenticated principal.
- Every create, supersede, status change, and report generation event is attributable and timestamped in UTC.
- Cross-station access and privilege escalation must fail closed.
- Do not grant permissions based only on a displayed role label.

## UI integration points

- Reports hub: entry to the archive register and monthly report.
- Hourly and daily report views: expose export batch/file metadata and a link to its archive status.
- Auditor review workspace: queue of exports awaiting archival, completed archive history, and reconciliation warnings.
- Network management workspace: missing-record/missing-data register and ownership/status updates.
- Monthly report view: UTC month selector, archive metrics, station/report breakdown, missing items, and downloadable PDF/Excel output when separately implemented and tested.

These pages must use the same station scope, report identifiers, and UTC period semantics. Do not create duplicate sidebars or separate, inconsistent copies of the archive status.

## Data/API approval gate

This document is a functional requirement only. It does not authorize a database schema, SQL migration, archive database connection, file upload integration, or production change.

Before implementation against persistent storage, review and approve:
1. canonical report/export batch identity and relationship to hourly/daily observation records;
2. exact archive audit-event fields and immutability strategy;
3. authority/station scope for auditors and the Head of Network Department;
4. digest calculation and file-size/row-count verification rules;
5. retention and access policy for exported Excel files and monthly reports;
6. API contract and negative authorization tests.

Until those approvals exist, implement only safe UI prototypes and tests that do not persist operational data or connect to either database.
