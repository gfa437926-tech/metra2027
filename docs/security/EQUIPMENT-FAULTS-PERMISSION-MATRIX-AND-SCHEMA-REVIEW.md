# Equipment Faults — Permission Matrix and Schema Review

**Status:** review artifact only; no executable SQL and no database changes authorized.  
**Repository:** `gfa437926-tech/metra2027`  
**Branch:** `work/equipment-fault-domain`  
**Target Supabase project:** `tbdnklyxjvbrilvnwgmq`  
**Scope:** Equipment Faults only; use the current METRA station catalogue, never legacy station data.

## 1. Review outcome

The current domain policy defines six permission codes and an explicit transition graph. Application services already enforce a validated actor ID, station scope, and action-specific permission before reaching the persistence port.

The logical schema proposal identifies:
- `public.station_catalogue(id)` as the approved station foreign-key target;
- `auth.users(id)` as the identity foreign-key target;
- `equipment_faults` as current state;
- `equipment_fault_audit` as append-only history.

The schema proposal's persistence section still describes a PostgREST invoker routine called by `service_role`. That conflicts with the later security decision to avoid `service_role` for Equipment Faults and use a dedicated restricted PostgreSQL login (Option A baseline). This document records the conflict; it does not silently rewrite or implement either path.

## 2. Permission matrix derived from current domain code

Permission codes below are grounded in `EquipmentFaultPolicy.cs` and the API contract. They are action permissions, not database roles.

| Operation / transition | Required permission | Additional mandatory checks |
|---|---|---|
| Create report in station | `equipment_fault.create` | Actor from validated JWT `sub`; station authorized server-side; initial state Submitted; append Created audit event |
| List station faults | `equipment_fault.read` | Trusted station context; station predicate applied before count/page |
| Read fault detail | `equipment_fault.read` | Query by both fault ID and persisted station ID |
| Submitted → UnderReview | `equipment_fault.review` | Persisted current status must still be Submitted |
| Submitted → Rejected | `equipment_fault.review` | Persisted current status must still be Submitted |
| UnderReview → Assigned | `equipment_fault.assign` | Persisted current status must still be UnderReview |
| UnderReview → Rejected | `equipment_fault.review` | Persisted current status must still be UnderReview |
| Assigned → UnderReview | `equipment_fault.review` | Persisted current status must still be Assigned |
| Assigned → InProgress | `equipment_fault.resolve` | Persisted current status must still be Assigned |
| InProgress → Resolved | `equipment_fault.resolve` | Persisted current status must still be InProgress |
| Resolved → InProgress | `equipment_fault.resolve` | Explicitly permitted rework transition |
| Resolved → Closed | `equipment_fault.close` | Persisted current status must still be Resolved |

No permission is defined for direct deletion, arbitrary status editing, changing reporter/station ownership, or direct audit mutation.

## 3. Mandatory state-machine constraints

The database write boundary must independently enforce, not merely trust the .NET pre-check:

- Only the transitions in the table above are permitted.
- Same-state transitions are invalid.
- `Closed` and `Rejected` are terminal.
- Undefined enum/status strings are rejected.
- The expected current status must match the persisted row at write time.
- The row must match both `fault_id` and `station_id`.
- State update and audit append are one atomic transaction.
- A failed audit append rolls back the state update.
- Actor identity is derived from validated server context, never a caller-supplied body field.
- Audit timestamps are generated by the database.
- Audit history cannot be updated or deleted by the runtime principal.

**Important:** If Option A uses a narrowly scoped invoker-rights transition routine, the login role needs the exact underlying privileges required by that routine. Those privileges must not accidentally permit bypassing the state machine. If this cannot be achieved with a safe invoker model, the design must be revised and reviewed before any DDL; do not silently switch to SECURITY DEFINER or broad table grants.

## 5. RLS and transaction-context model

RLS remains enabled and forced where compatible with the selected ownership model. The application principal must not have `BYPASSRLS`.

For each database operation:
1. Validate the inbound Supabase token at the API boundary.
2. Read actor UUID only from the validated `sub` claim.
3. Resolve station membership and action permission from the authoritative METRA authorization services and current station catalogue.
4. Begin a database transaction.
5. Set actor and authorized station context transaction-locally, not session-wide.
6. Execute only the parameterized, approved read/write operation.
7. Commit or roll back before returning the pooled connection.

Transaction-local settings are trusted API assertions, not independently authenticated identity. A compromised API process holding the database credential can forge custom settings. The API host and credential manager therefore remain part of the trusted computing base.

No client-provided station ID, actor ID, or role string may establish database authority.

## 6. Schema review questions still open

Before generating an executable migration or adapter, resolve these details explicitly:

1. **Schema placement:** Should the two tables live in `public` or a dedicated non-exposed feature schema? The current proposal mentions a dedicated API schema for a routine but does not finalize table placement.
2. **Routine boundary:** Will create and transition be separate routines? What exact routine owner and invoker model will preserve atomicity without broad direct table grants?
3. **Read boundary:** Will the restricted login receive SELECT on the fault table under RLS, or will reads use narrowly scoped routines/views? The current proposal does not define a complete read grant model.
4. **Audit reads:** Is a station-scoped audit-history endpoint required in this delivery, or is audit write-only for now?
5. **Creation reason:** The audit schema currently uses a 5–1000 character reason, but the create API contract does not yet clearly define a separate creation-reason field/rule.
6. **Audit event types:** Confirm exact canonical event strings and whether creation is represented as `Created` with `previous_status = NULL`.
7. **Actor deletion:** The proposal says reporter/actor FK deletion should be restricted or use an approved anonymisation policy; retention and account deletion behavior remain undecided.
8. **Station catalogue deletion:** Confirm station catalogue rows are retained/restricted rather than cascading into fault history.
9. **Default privileges:** The target project audit found broad default privileges for objects created by `postgres` in `public`. New objects must not inherit unintended grants; do not run a blanket revoke against existing objects as part of this feature.
10. **Indexes and count semantics:** Confirm expected filters and operational volume before finalizing indexes; page and count predicates must be identical and station-scoped.

## 7. HS256 legacy-token compatibility — current decision gate

The Dashboard confirms a current ECC P-256 signing key (ES256) and a previously used HS256 shared-secret key still retained for verification of unexpired tokens.

The API's current JwtBearer configuration uses the Supabase Auth authority/JWKS metadata. That is sufficient evidence of intended asymmetric validation, but it does not prove that local API validation can verify a legacy HS256 token: the HS256 verification secret is not published in JWKS, and no secret should be exported or copied into this API.

Safe next step:
- Test ES256 acceptance and malformed/expired/wrong-issuer/wrong-audience rejection in an isolated environment.
- For an unexpired legacy HS256 session, choose either a Supabase Auth server-side token-validation fallback (using the presented bearer token and public API key, with no token logging) or a deliberate refresh/re-authentication policy.
- Do not add HS256 to the local JwtBearer accepted-algorithm list unless the correct verification key is available through an approved secure mechanism.
- Do not export the legacy secret, weaken signature validation, or accept unsigned tokens.
- Record the chosen compatibility policy and its user impact before changing authentication code.

This is not yet an implemented compatibility solution.

## 8. Required integration tests

The eventual isolated PostgreSQL suite must execute using the actual restricted application principal, not the schema owner:

- privilege assertions for the exact role matrix;
- RLS and station A/B isolation for reads, counts, and writes;
- spoofed actor/station inputs rejected;
- all allowed and forbidden state transitions tested against the database;
- concurrent expected-status transition: exactly one writer succeeds;
- audit append failure rolls back the current-state update;
- audit UPDATE/DELETE/TRUNCATE denied to the runtime principal;
- pooled connection interleaving proves transaction-local actor/station context does not leak;
- cross-station and unknown fault responses are indistinguishable;
- TLS and connection configuration fail closed.
