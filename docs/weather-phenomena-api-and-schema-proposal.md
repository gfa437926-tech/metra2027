# عقد API ومقترح مخطط سجل الظواهر الجوية

## الحالة

هذه وثيقة تصميم ومراجعة فقط. لم يتم إنشاء جدول أو تنفيذ migration أو تعديل Supabase/RLS. لا يوجد اعتماد بعد لأنواع أعمدة قاعدة البيانات وسياسات الوصول.

المصدر المرجعي: `weather_phenomena.html`، وخاصة كائن `phenomenonData` في عملية بدء الظاهرة وكائن `updateData` في عملية الإنهاء.

## الحقول المستخدمة فعلياً في المصدر القديم

| المفتاح الأصلي | الاستخدام في المصدر | ملاحظات |
|---|---|---|
| `id` | تحديث السجل بعد البدء | نوع المفتاح غير محسوم هنا |
| `phenomenon_type` | نوع الظاهرة الجوية | نص |
| `phenomenon_date` | تاريخ الظاهرة | تاريخ محلي في المصدر |
| `start_time` | وقت البدء UTC | نص وقت `HH:mm:ss` |
| `end_time` | وقت الانتهاء UTC | فارغ أثناء النشاط |
| `phenomenon_duration` | مدة الظاهرة | تنسيق `HH:mm:ss` |
| `phenomenon_status` | نشطة / منتهية | القيم العربية كما في المصدر |
| `general_notes` | ملاحظات إضافية | نص اختياري |
| `user_email` | بريد المستخدم | يجب استبداله بمرجع هوية موثوق عند التصميم النهائي |
| `user_name` | اسم المستخدم | بيانات عرض، لا تثبت الهوية |
| `station_name` | اسم المحطة | يجب ربطه بمعرّف محطة وتكليف موثوق |
| `user_role` | صفة العمل | لا تستخدم كصلاحية موثوقة |
| `submission_date` | تاريخ الإرسال | تاريخ |
| `submission_time` | وقت الإرسال UTC | وقت |
| `report_type` | نوع التقرير | المصدر يرسل `phenomena_record` |
| `status` | حالة التقرير | المصدر يرسل `submitted` |
| `validation_status` | حالة التحقق | المصدر يرسل `pending` |
| `is_shared_with_station` | إشارة مشاركة المحطة | يجب ألا تسمح للعميل بتجاوز صلاحية المشاركة |
| `shared_at` | وقت المشاركة | timestamp |
| `created_at` | وقت الإنشاء | timestamp |
| `updated_at` | وقت التعديل | timestamp |

## قيم لا ينبغي اعتبارها أعمدة مؤكدة

- `start_time_local` و`end_time_local`: المصدر يضيفهما للعرض المحلي في الذاكرة بعد قراءة السجل؛ لم يثبت أنهما عمودان في قاعدة البيانات.
- `local_start_time`: قيمة مؤقت محلية في الذاكرة وليست حقل تخزين موثوقاً.
- `user_id` و`station_id`: غير موجودين في كائن الإدخال القديم، لكنهما مطلوبان في التصميم الآمن المقترح كمرجعين علائقيين مصدرهما الخادم.

## عقد التحقق المضاف

المسار: `POST /api/v1/observations/phenomena/validate`

الطلب:
```json
{
  "phenomenonType": "مطر خفيف",
  "phenomenonDate": "2026-11-01",
  "startTime": "06:15:00",
  "endTime": null,
  "generalNotes": "ملاحظات اختيارية"
}
```

الاستجابة:
```json
{
  "isValid": true,
  "issues": []
}
```

التحقق الحالي محدود إلى:
- وجود نوع الظاهرة.
- تاريخ صحيح بصيغة `yyyy-MM-dd`.
- وقت بدء صحيح بصيغة `HH:mm:ss`.
- وقت انتهاء اختياري؛ إن أرسل فيجب أن يكون بصيغة `HH:mm:ss`.

هذا endpoint للتحقق فقط، ولا ينشئ سجلاً ولا يصادق على المستخدم أو المحطة ولا يحسب المدة. لم أضف قيوداً غير موجودة في المصدر مثل قائمة مغلقة لأنواع الظواهر أو حد أقصى للملاحظات.

## مقترح التصميم الآمن للمراجعة

قبل إنشاء الجدول، نحتاج اعتماد القرارات التالية:
1. استخدام معرّف مستخدم داخلي موثوق `created_by_user_id` بدلاً من الاعتماد على البريد أو الاسم.
2. استخدام `station_id` كمفتاح أجنبي إلى سجل المحطات؛ اسم المحطة للعرض فقط.
3. تخزين التاريخ والوقت مع تعريف صريح للمنطقة الزمنية للمحطة. المصدر القديم يطرح ثلاث ساعات ثابتة؛ هذا لا يراعي التوقيت الصيفي، لذلك لا يصح تعميمه على جميع المحطات.
4. تحديد ما إذا كانت حالة الظاهرة `phenomenon_status` مستقلة عن دورة اعتماد النشرة `status` و`validation_status`.
5. منع المستخدم من تعيين `user_role` أو `created_by_user_id` أو `station_id` أو حقول المشاركة مباشرة من الطلب.
6. تفعيل RLS وسياسات القراءة/الإضافة/التعديل بعد مراجعة نموذج الهوية والتكليف النشط بالمحطة.
7. ضمان وجود ظاهرة نشطة واحدة فقط لكل مستخدم ومحطة إذا كان هذا هو السلوك التشغيلي المطلوب؛ يحتاج ذلك قراراً وقيداً على مستوى قاعدة البيانات.

## ما لم يتم تنفيذه

- لا توجد migrations أو جداول أو فهارس أو سياسات RLS جديدة.
- لا توجد endpoints لإنشاء/تعديل/قراءة السجلات.
- لا توجد مصادقة فعلية أو صلاحيات مرتبطة بمزود هوية.
- لا توجد مزامنة Angular أو Flutter مع هذا endpoint بعد.
