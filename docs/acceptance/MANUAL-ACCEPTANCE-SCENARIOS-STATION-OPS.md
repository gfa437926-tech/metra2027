# سيناريوهات قبول يدوي — الرصد وعمليات المحطة

**الغرض:** تحقق تشغيلي بدون الاعتماد على GitHub Actions في هذه المرحلة.  
**الفرع:** `work/legacy-ui-migration-audit`  
**UTC فقط في كل أوقات الرصد.**

## متطلبات الحسابات
- حساب راصد مخوّل لمحطة A فقط.
- حساب مراجع/رئيس محطة مخوّل لمحطة A (ليس نفس الراصد إن كان فصل الواجبات مفعّلاً).
- حساب مخوّل لمحطة B فقط (لاختبار العزل).

## أ) دورة الرصد
1. تسجيل دخول الراصد → اختيار محطة A من الدليل (يظهر الاسم والرمز على الرئيسية).
2. إدخال نشرة ساعية صحيحة → إرسال للمراجعة → ظهور إيصال id.
3. محاولة إدخال بقيم خارج المدى → رفض محلي أو 400 من الخادم دون مسح النموذج عند فشل الحفظ.
4. بحساب محطة B: فتح مراجعة محطة A عبر تلاعب بالمعرّف إن أمكن من الواجهة → يجب 403 أو منع الاختيار.
5. المراجع على A: طابور المراجعة → اعتماد نشرة ليست ملكه.
6. محاولة اعتماد ذاتي (إن وُجدت نشرة لنفس المستخدم) → 403.
7. إرجاع نشرة مع ملاحظة → تظهر في المُرجَع.
8. الراصد: محرر المُرجَع يعرض الملاحظة وUTC → تصحيح → إعادة تقديم → تعود لطابور المراجعة.
9. اعتماد نهائية → تختفي من الطابور.

## ب) الأعطال والدعم
1. على محطة A: تسجيل عطل → يظهر في القائمة.
2. انتقالات الحالة المسموحة فقط (مراجعة → إسناد → إصلاح → حل → إغلاق).
3. انتقال غير صالح أو بلا صلاحية → رسالة عربية واضحة (403/409).
4. نفس السيناريو لبلاغ دعم.
5. ملخص التشغيل يعكس أعداداً من API فقط.

## ج) الإدارة ضمن المحطة
1. مراجعة طلب تسجيل: موافقة/رفض مع ملاحظة الرفض.
2. تعيينات: طلب → قرار → إلغاء عند الحاجة.
3. أرشفة Excel يدوية: تأكيد سجل إداري دون ترحيل أرصاد.

## د) مركز التنبؤ (حد كتالوج)
1. كل حساب مفعّل يرى الدليل والمقارنة الجغرافية.
2. ملف المحطة: إحداثيات/ارتفاع من الكتالوج؛ **قيم رصد لحظية = غير متاحة**.
3. لا أزرار تعديل أرصاد من واجهة التنبؤ.

## نتيجة التوثيق
سجّل لكل خطوة: نجح / فشل / رمز HTTP / ملاحظات.  
أي فشل يُحوَّل إلى إصلاح كود على نفس الفرع دون تطبيق SQL.
