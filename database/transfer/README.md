# METRA 2027 — Experimental → Target Supabase Transfer Pack

**Source project (experimental only):** `tbdnklyxjvbrilvnwgmq`
**Target project:** to be named by the owner later.
**Forbidden:** any legacy METRA database outside the experimental project.
**Baseline:** `3fdc0593d08991d9e540d20fe973c790f7cd5b64`

## Purpose and safety boundary

Repeatable export/import from the approved experimental Supabase project to a future, explicitly identified target.
The source is never modified or deleted by this pack. It does not copy API keys, JWT secrets, Auth sessions, or refresh tokens.
The export writes AES-256 encrypted GPG dumps; the passphrase must be supplied through the secure shell environment and stored separately from the artifacts.

## Scripts

- `scripts/lib/project_url_guard.sh` — checks that a Postgres URL identifies the exact project ref
- `scripts/00_preflight.sh` — read-only source identity/connectivity check
- `scripts/01_export_source.sh` — encrypted public schema/data export plus SHA-256 manifest
- `scripts/03_import_schema.sh` — decrypts/imports public schema only into an empty target
- `scripts/04_import_data.sh` — decrypts/imports public data only into empty tables
- `scripts/05_compare.sh` — exact row counts and deterministic application-object inventory comparison
- `sql/assert_empty_public_tables.sql` — read-only guard that blocks data import into populated tables
- `tests/test_url_guard.sh` — direct-host, pooler-username, and wrong-project guard tests

There is no `02_inventory_source.sh`; inventory output is generated by `01_export_source.sh`.

## Secure environment

Never paste credentials or passphrases into chat or Git. Set them in a protected local shell/secret manager:

```bash
export METRA_SRC_PROJECT_REF=tbdnklyxjvbrilvnwgmq
export METRA_SRC_DATABASE_URL='postgresql://...'
export METRA_TRANSFER_PASSPHRASE='use-a-long-random-secret-from-your-secret-manager'
export METRA_DST_PROJECT_REF='<new-ref>'
export METRA_DST_DATABASE_URL='postgresql://...'
```

The URL guard supports direct `db.<ref>.supabase.co` hosts and Supavisor usernames `postgres.<ref>`. If the URL cannot prove the expected ref, the script refuses to proceed.

## Comparison scope

- Row counts use exact `COUNT(*)` for each public/private table; this can be expensive on large datasets.
- Object comparison checks the names and selected signatures/types of listed public/private objects. It is not a byte-for-byte schema-definition comparison.
- Auth, Storage, extensions, grants, secrets, provider settings, and user identities are outside this automated transfer scope.

## Automated validation

`.github/workflows/transfer-pack.yml` runs shell syntax checks, URL-guard tests, PostgreSQL SQL checks in a disposable PostgreSQL 16 service, and a GPG encryption/decryption round trip. These checks do not connect to Supabase and do not prove a live export/import.

## Auth and restore status

Auth users are not exported or imported. Use the separately reviewed Auth transfer procedure and recreate accounts with target-side credentials; never copy active sessions or source JWT secrets.
A successful script run is not a restore acceptance. A full restore drill, application smoke tests, row/object comparison, and owner sign-off remain required.

## Live dump status

No hosted export, target import, restore drill, or live cutover is claimed by this repository change. The scripts require secure runtime credentials and an explicitly named new target.
